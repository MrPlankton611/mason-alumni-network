# Design: Shared-partial templating for header/footer

## Goal

Eliminate duplicated header and footer markup across `alumni/index.html`, `alumni/college-level.html`, and `alumni/career-level.html` by introducing a minimal build-time templating system — no new frameworks, no new runtime dependencies, and no disruption to the existing local-dev (`npm start`) or deploy (`.github/workflows/pages.yml`) workflows from the user's perspective.

## Why this is needed now

The Mason-brand-alignment plan's Task 5 (icon rail) was originally written to duplicate a new shared HTML block into all three pages, matching the existing header/footer duplication pattern. The user asked for real templating instead — covering the icon rail plus the two blocks that are already duplicated (header, footer) — rather than adding a fourth duplicated block on top of two existing ones.

## Current state

- `alumni/*.html` — 3 static pages, each with its own `<header>...</header>` and `<footer>...</footer>` block. These blocks are ~95% identical between pages; the differences are: the tagline text in `.site-title .tagline`, and which nav tab/dropdown carries `active`/`open`.
- `alumni/styles.css`, `alumni/*.js`, `alumni/assets/*` — shared, already single-sourced, not duplicated. Not part of this change.
- `package.json` scripts: `start`/`serve:alumni`/`serve` all just run `http-server` directly against the repo — no build step exists today.
- `.github/workflows/pages.yml` — on push to `main`, checks out the repo, runs a `sed`-based cache-busting step against `alumni/*.html` (appends `?v=$SHA` to `styles.css`/`share.js` references), then uploads `alumni/` as the Pages artifact. No build step exists today.

## Design

### New source directory: `alumni-src/`

- `alumni-src/pages/index.html`, `college-level.html`, `career-level.html` — the source of truth for each page. Identical to the current `alumni/*.html` files except the `<header>...</header>` and `<footer>...</footer>` blocks are replaced with single-line marker comments:
  ```html
  <!-- INCLUDE:header page="home" tagline="Comets Forever, Connected Always" -->
  ```
  ```html
  <!-- INCLUDE:footer -->
  ```
  `page` is one of `home`/`college`/`career`; `tagline` is the exact text currently in that page's `.tagline` span.

- `alumni-src/partials/header.html` — the shared header markup, with two placeholders:
  ```html
  <header class="header">
  	<div class="header-main">
  		<div class="container">
  			<div class="logo-section">
  				<a href="index.html" class="logo-link">
  					<img src="assets/alumni_network_logo.png" alt="Comet Alumni Network" class="logo">
  				</a>
  				<div class="site-title">
  					<h1>Comet Alumni Network</h1>
  					<span class="tagline">{{TAGLINE}}</span>
  				</div>
  			</div>
  {{NAV}}
  		</div>
  	</div>
  </header>
  ```
  `{{TAGLINE}}` is a plain string substitution from the marker's `tagline` attribute. `{{NAV}}` is substituted with HTML generated by `scripts/build.js` (see below) — it is not a plain text placeholder, because the nav's active/open state differs structurally between pages (which tab has `class="active"`, which `<details>` has the `open` attribute), not just by text content.

- `alumni-src/partials/footer.html` — the shared footer markup, verbatim, no placeholders (confirmed identical across all three pages today).

### Build script: `scripts/build.js`

Plain Node (`fs`, `path` only — no new dependencies). For each file in `alumni-src/pages/`:
1. Read the page template.
2. Find every `<!-- INCLUDE:name key="value" ... -->` marker via regex.
3. For `footer`: read `alumni-src/partials/footer.html` verbatim, substitute in place of the marker.
4. For `header`: read `alumni-src/partials/header.html`, substitute `{{TAGLINE}}` with the marker's `tagline` attribute, substitute `{{NAV}}` with the output of an internal `buildNav(pageId)` function (a small `switch`/lookup over `'home'|'college'|'career'` that returns the exact nav HTML for that page, matching today's per-page markup byte-for-byte), then substitute the whole result in place of the marker.
5. Write the fully-resolved HTML to `alumni/<same-filename>.html`.
6. Throw a clear error (and exit non-zero) if a marker references a partial name the script doesn't recognize, or if a required attribute (`page`, `tagline`) is missing — this is a build tool, so fail loudly rather than silently emitting broken HTML.

This is the only new file with executable logic in this sub-project. It does not touch `alumni/styles.css`, `alumni/*.js`, or `alumni/assets/*` — those stay exactly as they are today, hand-edited directly, not part of the build.

### Generated files become gitignored

Add to `.gitignore`:
```
/alumni/index.html
/alumni/college-level.html
/alumni/career-level.html
```

These three files are now build output. Everything else currently in `alumni/` (CSS, JS, assets, the other page-adjacent files like `donate-tracking-setup.md`) stays tracked exactly as before.

### Local dev workflow (unchanged from the user's perspective)

Add to `package.json`:
```json
"scripts": {
  "build": "node scripts/build.js",
  "prestart": "npm run build",
  "preserve:alumni": "npm run build",
  "start": "http-server . -p 8000 -o /alumni/ -c-1",
  "serve:alumni": "http-server . -p 8000 -o /alumni/ -c-1",
  "serve": "http-server . -p 8000 -c-1"
}
```
`prestart`/`preserve:alumni` are npm's automatic pre-hook convention — `npm start` and `npm run serve:alumni` now build first, silently, with no change to how the user invokes them. (`npm run serve` — the bare root-serving variant — does not get a pre-hook, since it's used to browse the raw repo including `alumni-src/`, not specifically the alumni site.)

### CI workflow

Add one step to `.github/workflows/pages.yml`, immediately after `actions/checkout@v4` and before the existing cache-busting `sed` step:
```yaml
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Build pages from templates
        run: node scripts/build.js
```
The existing cache-busting step operates on `alumni/*.html` exactly as it does today — it runs after the build step, so it's sed-ing the freshly generated files, unchanged in behavior.

## Explicitly out of scope

- **Icon rail markup** — stays with the visual-alignment plan's Task 5. Once this lands, Task 5 becomes: create `alumni-src/partials/icon-rail.html` (one file), add `<!-- INCLUDE:icon-rail -->` to each of the three page templates (one line each), rather than duplicating a full block three times.
- **Templating `styles.css`/JS/assets** — these are already single-sourced (one file each, referenced by all pages), not duplicated, so there's nothing to template.
- **A general-purpose templating engine or static site generator** — the marker/partial mechanism here is intentionally narrow (two known include names, one computed substitution for nav) rather than a reusable engine, since this site has exactly three pages and two shared blocks. Reaching for something like Eleventy would be new-framework overhead for a problem this small.

## Files touched

- Create: `alumni-src/pages/index.html`, `alumni-src/pages/college-level.html`, `alumni-src/pages/career-level.html` (migrated from current `alumni/*.html`, header/footer replaced with markers)
- Create: `alumni-src/partials/header.html`, `alumni-src/partials/footer.html`
- Create: `scripts/build.js`
- Modify: `package.json` (add `build` script, `prestart`/`preserve:alumni` pre-hooks)
- Modify: `.github/workflows/pages.yml` (add Node setup + build step)
- Modify: `.gitignore` (ignore the 3 generated HTML files)
- Delete (from git tracking, since they become generated output): the current `alumni/index.html`, `alumni/college-level.html`, `alumni/career-level.html` — regenerated by the build script instead

## Verification approach

No existing test suite. Verification is: run `node scripts/build.js`, diff the generated `alumni/*.html` against the pre-migration versions (from git history) to confirm byte-for-byte equivalence for the header/footer/nav sections (the only thing that should differ, if anything, is incidental whitespace at the marker boundary — not content), then serve the site and visually/functionally re-verify nav dropdown hover behavior, share popup, and donate tracking all still work exactly as before (these are regression risks since this touches every page's markup, even though the content itself shouldn't change).
